# Event Schema and Evidence Contract

## Purpose

A shared event contract is needed so attack execution, detection, validation, replay, and scoring can reason about the same session and technique. The fields below reflect the documented normalized-event concept. Implementations must be checked against `shared/schema.py`, `services/ingestion/normalizer.py`, database definitions, and actual producer payloads before treating this as a strict production contract.

## Core event fields

| Field | Intended meaning | Validation expectation |
|---|---|---|
| `event_id` | Stable unique event identifier | Required; unique within the relevant store. |
| `tenant_id` | Tenant/security boundary | Set by trusted application context; never trust arbitrary incoming raw payload for this value. |
| `session_id` | Session/lab execution identifier | Required for session-bound events; nullable only for explicitly sessionless events. |
| `scenario_id` | Scenario identifier | Optional when event is not generated by a scenario. |
| `build_id` | Build or release candidate identifier | Optional where not applicable; trusted binding must be preserved. |
| `timestamp` | Event time | ISO-8601 timestamp with timezone; document source and ingestion times separately if both are needed. |
| `source_type` | Producer class such as attack, host, network, SOC, or detection | Controlled vocabulary, validated at ingestion. |
| `source_name` | Specific producer/sensor/tool | Optional but recommended for provenance. |
| `actor` | Principal/process/user involved | Optional; normalize safely. |
| `action` | Activity or event description | Required for useful detections; preserve raw evidence separately. |
| `mitre_tactic` | ATT&CK tactic identifier/name | Optional; validate against the selected ATT&CK version. |
| `mitre_technique` | ATT&CK technique ID | Optional; must not imply coverage by itself. |
| `severity` | Normalized severity | Use a documented controlled vocabulary. |
| `outcome` | Result/status | Must distinguish simulated, live, blocked, failed, and inconclusive outcomes where applicable. |
| `replay` | Whether event is replay-generated | Boolean; replayed events must not be counted as new live attacks. |
| `raw_payload` | Original producer payload | Store with bounded size/access controls; avoid uncontrolled indexing of arbitrary fields. |

## Evidence provenance requirements

- A raw event cannot assign trusted `tenant_id`, `session_id`, or `build_id` merely by including them in its payload.
- A simulated event must carry a simulation marker or equivalent trusted execution mode.
- A replayed event must be marked as replay and excluded from fresh live-coverage calculations.
- A detection should reference the event(s) that triggered it, or retain an explicit correlation record.
- ATT&CK coverage should require a live attack record and linked detection evidence under the validation policy; a technique label alone is insufficient.
- Missing telemetry, unavailable sensors, invalid PCAPs, and scanner failures should produce unavailable/inconclusive states, not fabricated success or findings.

## Schema conformance tests

Before calling this schema verified, test:

1. Every event producer against the required fields and types.
2. Invalid timestamps, unknown source types, oversized payloads, and malformed identifiers.
3. Tenant/session/build spoofing attempts.
4. Database and OpenSearch mapping compatibility.
5. Duplicate delivery and replay idempotency.
6. Correlation between attack event, sensor event, and detection.
7. Schema evolution compatibility for archived events.

## Schema change policy

Any field rename, type change, enum change, or correlation-rule change must update the schema, producer/consumer code, storage mappings, tests, and migration notes together. Version the event contract when backward compatibility cannot be maintained.
